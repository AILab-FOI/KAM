# Publication benchmark protocol (design freeze candidate)

Target venue: **Simulation Modelling Practice and Theory (SIMPAT)**.

The protocol separates **pilot/calibration experiments** from **confirmatory experiments**. Built-in parameter-only pilot generators are not sufficient for the paper's final four-domain claim.

## 1. Research questions

**RQ1 — Effectiveness.** Do C-KAM and D-KAM improve dynamic organization relative to non-adaptive, single-objective, and strong multi-objective baselines?

**RQ2 — Decentralization gap.** How much solution quality is lost (or changed) by holonic D-KAM relative to centralized C-KAM?

**RQ3 — Scalability/overhead.** How do candidate evaluations, decision time, control-message hops, and local information footprint scale with system size and holarchy depth?

**RQ4 — Robustness.** How does D-KAM respond to stale/noisy/incomplete observations and rapid environmental change?

**RQ5 — Generality.** Does one unchanged KAM adaptation core exhibit useful behavior across four domain-specific benchmark models?

## 2. Primary outcomes

Do **not** use the optimized objective as the sole evidence. The primary observable outcomes are:

1. cumulative completion ratio (higher is better);
2. mean backlog / capacity and post-disturbance backlog AUC (lower);
3. raw capacity-share load imbalance (lower);
4. makespan/utilization proxy (lower);
5. cross-unit communication ratio and normalized communication cost (lower);
6. reorganization cost/migrations (lower conditional on comparable performance);
7. for decentralization: control-message hops and candidate evaluations (lower conditional on comparable performance).

KAM capacity mismatch, management overhead, and the composite objective are mechanistic/secondary outcomes.

## 3. Core baseline panel

Run in all four domains unless a domain makes the method nonsensical:

- **Static** — no adaptation.
- **Greedy load balancing** — MOVE decisions based only on raw load/overload.
- **Affinity greedy** — MOVE decisions based predominantly on communication affinity.
- **Balanced affinity** — strong non-KAM multi-objective MOVE baseline using raw balance + overload + communication + migration cost.
- **Dynamic Leiden** — established Leiden community detection initialized from the current partition, with maximum-overlap remapping and a predeclared migration budget; no KAM factors.
- **C-KAM**.
- **D-KAM**.

`Random feasible` remains a software/sanity control and should normally be omitted from the main paper figures.

## 4. Domain-specific baselines to add before confirmatory runs

### Warehouse/logistics
At least one auction/market-based or cost-based task/team reassignment method. If the final generator models spatial motion, include a distance/travel-aware greedy policy.

### Edge/IoT
A resource-and-latency-aware placement/migration heuristic that minimizes overload and network cost without KAM factors.

### Enterprise/project organization
Leiden/community-based team formation is the principal structural baseline; optionally add a task-affinity reassignment heuristic.

### HPC
Include work stealing and **ParMETIS `ParMETIS_V3_AdaptiveRepart`** as the primary established comparator. KAM-Bench invokes it through the versioned external partition protocol and bundled MPI/C++ helper; the returned placement is applied directly. Zoltan remains a useful replication/extension option because it is a broader dynamic load-balancing toolkit and can interface to ParMETIS, but it is not required for C1.

## 5. Publication-grade use-case designs

### 5.1 Warehouse/logistics benchmark

**Agents:** autonomous robots or work cells represented as persistent workers.
**Leaf units:** teams/zones/resource pools.
**Work:** orders/task service requirements generated from spatial demand hotspots.
**Communication:** collision avoidance, handoff, shared-order and route coordination induced by spatial/task overlap.
**Disturbances:** moving demand hotspot, aisle/zone capacity reduction, burst of urgent orders.
**Migration cost:** reassignment/handover plus optional distance to the new zone/team.
**Required distinguishing mechanism:** communication and work must derive from a spatial/task model, not a stochastic block matrix with warehouse-specific constants.

### 5.2 Edge/IoT benchmark

**Agents:** migratable services/service replicas or persistent service actors.
**Leaf units:** edge resource pools.
**Work:** CPU/memory-equivalent demand generated by request traces.
**Communication:** service-call/data-flow graph weighted by traffic.
**Disturbances:** regional demand burst, capacity degradation/failure, changed service graph.
**Migration cost:** service state size / available transfer bandwidth proxy.
**Required distinguishing mechanism:** workloads and communications should be generated by service chains and regional demand, or imported from a public/measured trace.

### 5.3 Enterprise/project benchmark

**Agents:** people or software agents with persistent skill/activity profiles.
**Leaf units:** project teams/departments.
**Work:** task packages requiring activity/skill bundles.
**Communication:** collaboration induced by shared tasks/dependencies and information exchange.
**Disturbances:** project-phase transitions, new project, deadline-driven hotspot, temporary capacity loss.
**Migration cost:** handover/context switching/reassignment.
**Required distinguishing mechanism:** overlapping project/task dependency structure rather than the same block model used in technical domains.

### 5.4 HPC load-balancing benchmark

**Agents:** migratable work units, analogous to overdecomposed objects/chare-like tasks.
**Leaf units:** scheduler/resource pools, not immutable hardware components; physical capacity is conserved when organizational pools split/merge.
**Work:** per-object compute time.
**Communication:** weighted task graph.
**Disturbances:** stragglers, changing adaptive-mesh/particle hotspots, resource slowdown/failure.
**Migration cost:** state size / transfer-rate proxy.
**Important interpretation:** KAM MERGE/SPLIT changes *scheduling/organizational domains*, not the existence of physical processors. A domain-specific placement baseline handles direct task-to-processor assignment.

## 6. Experimental phases

### Phase P0 — software verification
Small deterministic/smoke runs. No scientific conclusions.

### Phase P1 — calibration pilot
Use a disjoint, predeclared pilot seed set (suggested 10–20 seeds per domain). Calibrate only:

- objective weights;
- minimum improvement threshold;
- adaptation interval;
- split minimum size;
- D-KAM target/proposal limits;
- scenario disturbance magnitudes if needed to avoid trivial zero-load or impossible-overload regimes.

Select parameters by a written rule (e.g. balance comparable objective-component scales plus stability constraints), **not by maximizing C/D-KAM's rank against baselines**.

A separate **P2 comparator-only pilot** freezes Leiden migration-budget/iteration settings and ParMETIS `ubvec`/`ipc2redist` using only comparator-internal quality/overhead tradeoffs. P1 C-KAM/D-KAM parameters remain untouched.

### Phase C1 — main confirmatory benchmark
Suggested starting design:

- 4 domains;
- 50 independent confirmatory seeds/domain;
- 200 steps/run;
- 20-step pre-adaptation/warm-up period (`adapt_start_step=20`);
- 4 scheduled disturbances after warm-up;
- moderate system size chosen so all principal methods complete (initial target: 64–128 agents and 8–12 leaf units; HPC may use a larger separate domain run if C-KAM remains feasible).

All algorithms receive identical exogenous arrivals/communication/capacity/disturbances for the same domain/seed.

### Phase C2 — scalability
For D-KAM, C-KAM, balanced affinity, and the strongest structural/load baseline:

- `N = {32, 64, 128, 256, 512, 1024}` where feasible;
- hold mean leaf size approximately constant so `K` grows with `N`;
- 10–20 independent seeds per point;
- report candidate evaluations, wall time, control-message hops, memory if profiled, and performance quality.

C-KAM may be stopped beyond a predeclared runtime limit; report the limit rather than silently dropping large cases.

### Phase C3 — D-KAM delay/robustness
At a fixed moderate size:

- observation delay `d = {0,1,2,4,8}`;
- later add message loss/noise once those mechanisms are implemented;
- measure actual-vs-estimated operation delta, worsening-operation frequency, completion/backlog, and control overhead.

### Phase C4 — ablation
Compare full KAM with:

- MOVE only;
- MOVE+MERGE;
- MOVE+SPLIT;
- full MOVE+MERGE+SPLIT;
- balanced-affinity non-KAM counterpart;
- optionally neutralize `kq`, `kc`, `ks` to isolate the role of KAM weighting.

### Phase S — sensitivity (not hypothesis confirmation)
Vary objective weights and thresholds around the frozen values. Report whether qualitative conclusions change. Keep this separate from C1 hypothesis tests.

## 7. Statistics

- The **seed/run** is the independent inferential unit. Time steps are repeated measurements within a run and must not be treated as independent samples.
- Use a Friedman test across methods for each domain/primary outcome, with Kendall's W.
- Planned post-hoc contrasts: C-KAM vs each strong baseline, D-KAM vs each strong baseline, and D-KAM vs C-KAM.
- Use paired Wilcoxon and/or paired t summaries with Holm correction; emphasize effect sizes and confidence intervals rather than p-values alone.
- Report all confirmatory seeds, including runs in which a method performs poorly or fails. Failures/timeouts need predefined handling.

## 8. Weight/threshold freeze rule

The final JSON configuration used for C1 is generated **before** C1 runs and stored with SHA-256. Any parameter change after viewing C1 outcomes creates a new protocol version and a new confirmatory seed set.

## 9. Reproducibility package

Archive:

- source release/tag;
- frozen configuration JSON;
- pilot and confirmatory seed lists;
- trace hashes or public trace identifiers;
- raw step/event/assignment output;
- environment manifest;
- scripts/notebooks that produce every table and figure in the paper.
